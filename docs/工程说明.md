## 2. 架构：三条红线

这三条是整个项目能一直改下去的原因，改代码前请先确认没有违反：

1. **`src/engine` 不认识 React、不碰 DOM、不读 `Date.now()`。** 所有随机都来自传入的 seed。
   → 因此引擎可以在 Node 里直接测、可以回放、可以克隆给 AI 用。
2. **`GameState` 必须 100% JSON 可序列化**（不存 Map/Set/类实例/函数）。
   → 因此"撤销 = 快照栈""存档 = JSON.stringify""AI 推演 = structuredClone"三件事全部免费。
3. **`applyMove(state, action)` 返回 `{ state, events }`。** UI 只渲染 events，不自己推算规则。
   → 因此改 UI 不可能改坏规则，规则只有一处实现。

模块职责：

```
src/engine/     纯逻辑。types / hex / rng / board / gameBoard / setup / moves / apply
                / scoring / capabilities / config / data/{boards,tiles,buildings,knowledge,scoring}
src/ai/         只通过引擎公开接口行动（listLegalMoves / applyMove / 公开状态），结构上不可能作弊
src/store/      对局状态容器（zustand）+ 撤销快照栈 + 自动存档（IndexedDB）+ 导入导出
src/ui/         React 界面。selection.ts 是"引擎合法行动 → 界面可点区域"的唯一翻译层
src/editor/     版图录入器（独立入口 editor.html）
tools/          部署、部署自检、离线检查、布局量测、图标生成、规则书文本抽取
```

## 3. 测试策略

分五层，**每层测的东西不同**，别把某一层的绿灯当成整体的绿灯：

| 层 | 位置 | 覆盖什么 | 用例数 |
|---|---|---|---|
| 几何与随机 | `hex / rng` | 六边形距离与连通块、随机数可复现 | 19 |
| 规则数据 | `board / tiles / knowledge / scoring / buildings` | 数据自洽 + **与官方规则书逐条对齐的"保真度锁"** | 86 |
| 规则执行 | `moves / apply / setup / settlement / capabilities / knowledgeEffects` | 行动合法性、效果结算、计分、初始化与守恒 | 138 |
| AI | `heuristic` | 评估单调性、分层强度、**批量自对弈无退化** | 21 |
| 界面与存储 | `render / selection / interaction / threats / persistence / vpDelta / offlineReady / model` | 渲染不崩、真实点击链路、存档编解码、威胁分析 | 88 |

> 上表是**源码里字面写出的 `it(` 个数**，合计 352；`pnpm test` 报 361，
> 差的 9 个来自循环生成的用例（八种建筑的计分板块、三张"从任意仓库取板块"的建筑）。
> 改动测试后若要更新这张表，请以 runner 的数字为准。

几个值得保留的习惯：

- **不变量断言**：`assertInvariants`（板块总数恒为 164、仓储 ≤3、货物颜色 ≤3、资源非负、
  板块 id 全局唯一）在随机对局里每 37 步查一次。
- **必须"真的打完"**：`randomPlayout` 与 `playMatch` 都断言 `state.finished`。
  这一条是踩坑后加的 —— 早先遇到步数上限只是静默退出，于是一个活锁被当成了正常对局。
- **多种子批量覆盖**：20 局随机对局 + 8 局 AI 自对弈，随机走法最容易撞到冷门规则组合。
- **"一条不落"型断言**：规则速查面板对 26 张知识板块、8 种建筑逐条断言渲染出来。
- **测量工具本身也要被审视**：本 session 出现过 4 次"问题在测试/指标而不是被测代码"
  （恒为 0.5 的废指标、离线检查的时序与错误前置条件、测试助手基线取错、没限定骰子序号）。
  **看到红灯先怀疑测量方式，看到绿灯也一样。**

## 4. 部署与自检

- 线上：GitHub Pages，源 = `gh-pages` 分支（**只有构建产物**）。源码在 `main`。
- **为什么不用 GitHub Actions**：当前 `gh` token 没有 `workflow` 作用域，推 `.github/workflows/`
  会被 GitHub 拒绝。工作流内容保留在 `docs/github-actions-deploy.yml.example`，
  需要时先 `gh auth refresh -s workflow` 再复制回去。
- **仓库是公开的**：GitHub Pages 在免费账户下只支持公开仓库（私有仓库返回 422）。

`node tools/deploy-pages.mjs` 会自动做三件事：推 `gh-pages` → 等线上换成新构建 →
跑 `tools/check-deploy.mjs`（**39 项资源图自检**：index.html 引用的每个资源、manifest 的每个图标、
`sw.js` 预缓存清单的每一条都要 200，且预缓存路径必须全是相对路径）。

其他脚本：

| 脚本 | 用途 | 可靠性 |
|---|---|---|
| `check-deploy.mjs` | 部署后资源图自检 | 可靠，已接入部署流程 |
| `measure-narrow.ps1` | **精确 CSS 视口**下量布局（用 iframe 绕开 Windows 无头 Chrome 的 500px 最小窗口宽度） | 可靠 |
| `measure-layout.ps1` | 直接开窗口量布局（适合宽视口） | 可靠 |
| `check-offline.ps1` | 断网后能否打开 | ⚠️ **不可靠**，见下 |
| `extract-rulebook.py` | 从规则书 PDF 抽文本（环境无 PDF 工具，靠 pypdf + fontTools） | 一次性 |

**`check-offline.ps1` 的三种退出码**：`0` 测出来离线可用 / `1` 测出来离线不可用 /
`2` **无法测量**。在 Windows 无头 Chrome 上，Service Worker 状态跨进程持久化与探针时序
都不受控制，重跑经常拿不到探针结果。**读不到一律算"无法测量"，绝不把"没测到"说成"离线不可用"。**
决定性验证在真机上（第 6 节）。

## 5. ⚠️ 占位数据清单

**这一节最重要。** 下面这些是"逻辑正确、数据是造的"。它们不会让程序崩，但会让体验与实物不一致。

| # | 占位的是什么 | 影响 | 怎么换掉 |
|---|---|---|---|
| 1 | **玩家版图布局**：`data/boards/synthetic.ts` 的合成 37 格六边形版图顶替 1 号版图 | 区域形状、AI 的区域规划、威胁提示、"差几格完成"的数值**全是按合成版图算的** | 用录入器（`/editor.html`）产出 JSON → 替换 `src/engine/config.ts` 里的 `playerBoards['1']` |
| 2 | **中央版图仓库色位**：占位版图每阶段 12 个格位、每色各占 2 个仓库 | "哪个点数能拿到什么颜色"、供应堆耗尽速度 | 需要 2 人局棋盘（翻转面）的照片 |
| 3 | **动物板块的只数分布**：每种 5 枚绿背里 2/3/4 只各几枚 | 动物计分的具体数值 | 规则书组件清单没给，需要看实物板块 |
| 4 | **哪 6 张知识板块是黑背面** | 黑洞里能买到什么 | 看实物黄板块的背面 |
| 5 | **2 人局黑洞开局抽几枚**（当前 2 枚） | 每阶段可购买次数 | 规则书原文只说"按人数抽 2–8 枚" |

另有两处**规则书本身没写清**的：

- **市政厅的额外放置是否也取消点数限制**。规则书正文只说"再放一枚"，**完全没提颜色**
  （我已核对原文）。当前默认：保留点数限制（更保守的读法），开关在

- **6 号知识板块**用的是 **Special Edition** 的效果（"每回合限一次，花 2 个工人取一枚米色建筑"）。
  经典 alea 版是"可从全部 7 个仓库购买"。以你手上的版本为准，代码里一处常量即可切换。

### 已经核实过的（可以信任）

- **164 枚板块的逐色数量**：官方规则书第 2 页组件清单，逐项对得上
  （建筑 40+16、动物 20+8、矿 10+2、船 20+6、知识 20+6、城堡 14+2）。
- **26 张知识板块的效果**：规则书第 11–12 页逐条录入。
- **8 种建筑的效果与颜色**：规则书第 8–9 页逐条录入（市场 = 船或动物、木工坊 = 建筑、
  教堂 = 矿/知识/城堡、客栈 4 工人、银行 2 银币、瞭望塔 4 分）。
- **区域大小 → 分数是三角数**（1/3/6/10/15/21/28/36）。依据：规则书说"1–8 格给 1–36 分"，
  且一份第三方攻略提到"普通五格区域只有 15 分"这个锚点。⚠️ **分数表印在版图上，规则书文本里没有**，
  所以这是高置信推断而非直接核实 —— 你有实物的话顺手确认一下。
- **阶段奖励 10/8/6/4/2**：规则书说"从第一阶段 10 分到最后一阶段 2 分"，中间三个值是推断。

**加一张玩家版图**：用录入器导出 JSON，放进 `src/engine/data/boards/`，
在 `config.ts` 的 `playerBoards` 里登记。引擎会立刻用上（`validatePlayerBoard` 会保证数据自洽）。

**加一张知识板块**：在 `data/knowledge.ts` 的 `KNOWLEDGE_TILES` 加条目；
如果是"改规则"型，同时在 `capabilities.ts` 派生一个能力、在规则代码里读能力
（**不要在规则代码里写 `if (knowledgeId === N)`**）；最后补一条测试。

**调 AI 强度**：改 `ai/heuristic.ts` 顶部的 `HARD_BEAM_WIDTH` 与 `HARD_EVALUATION_BUDGET`，
然后跑 `pnpm test`，看输出的三行：`[性能] hard 单次回合搜索耗时`、
`[难度分层] hard vs normal`、`[批量自对弈]`。
**先看数字再改参数** —— 我一次估 375ms 实际 21ms，估错了一个半数量级。

**加一种新的结算**：在 `apply.ts` 里加事件 + 改状态，UI 只需要在 `ui/eventText.ts` 加一句中文描述。

## 8. 已知的坑

- **板块 id 必须全局唯一**：有色背面与黑背面是两副独立牌堆，`buildTilePool` 必须传不同前缀，
  否则两副牌里的 `building-001` 会撞车，而仓储/领地都是靠 id 引用板块的。
- **阶段开始要把棋盘上剩余板块移出本局**（收回盒中），不是放回供应堆。放回去会让供应堆取之不尽。
- **"效果引发的子选择"走 `state.pending`，不编进 Move**，否则动作空间会组合爆炸。
- **回合结束是显式动作**（`endTurn`）。官方允许在"两个骰子行动之后"买黑洞板块，
  自动结束回合会让玩家永远买不了。
- **`position: sticky` 而不是 `fixed` 的操作条**：`fixed` 需要用一个猜出来的高度给内容留白，
  而那个数字必然会错（实测真实高度 143px，我当时猜的是 132px）。sticky 让它自己占布局空间。
- **不要给 `.hexboard` 加 `overflow: visible`**：SVG 会溢出布局盒、画到上方文字上面。
- **界面层的随机数也必须来自 `GameState`**：AI 的决策随机源由 `decisionRng(state)`
  从局面派生，**不要用 `useRef` 持有随机状态，也不要用 `Math.random()`**。
  曾经有两处破例（组件内的 ref、`random.ts` 里的 `Math.random()`），后果是
  撤销之后 AI 会改下另一手、读档之后行为也会变 —— 而且这类问题**不会让任何断言变红**，
  只能靠"决策是否只取决于局面"这条契约去钉。契约在
  `src/ai/__tests__/opponentMove.test.ts`，改动 AI 调用方式时请一并跑它。
  （唯一合法的 `Math.random()` 是 `store` 里生成新局种子的那一处 —— 新局本来就需要新种子。）
- **动作交给 `play` 之前要核对它此刻是否仍然合法**：`store.play` 用已缓存的合法动作列表比对
  （`moveKey`），不合法的一律忽略。理由：按钮持有的是渲染那一刻的动作，
  手机快速连点会送来陈旧动作，而 `applyMove` 对已用过的骰子会**抛异常** ——
  异常发生在 React 事件处理器里，没有边界就是白屏。这不是"吞掉引擎错误"：
  真正的引擎 bug 发生在合法性判断之后，照旧会抛。
- **必须有错误边界**（`ui/components/ErrorBoundary.tsx`，挂在两个入口最外层）。
  这是个要在**飞机上离线玩**的应用，没有边界时任何未捕获异常都是白屏、且没有任何恢复入口。
  存档在 IndexedDB 里不会丢，所以兜底界面只需要说清"刷新即可回到最近保存的局面"并给按钮。
- **`.ps1` 脚本必须带 BOM**（见第 1 节）；**.ts/.mjs/README 用无 BOM 的 UTF-8**。
- **可点区域只能在轮到人类时派生**：`dieAffordances` / `pendingAffordances` 都要带 `isHumanTurn` 判断。
  因为 `moves` 是**当前行动方**的合法动作，轮到对手时它就是对手的动作；
  而清空 `selectedDie` 的 effect 在绘制**之后**才跑，存在"新状态已渲染、选中状态还没清"的窗口，
  窗口里点亮的格子属于对手 —— 点下去就是替对手走棋，而且那类动作在 store 的合法动作表里，
  第 25 轮那个守卫也拦不住。界面层做闸门，结构上就不可能越权。
- **自动存档必须在页面隐藏时立刻落盘**：`store.saveNow()` 由 `App` 里的
  `visibilitychange` / `pagehide` 监听调用。自动存档是 400ms 防抖，
  玩家在窗口内切走应用或锁屏，这一次操作就白做了；而 iOS 对主屏 PWA 的后台回收相当激进，
  手机又是这个应用的唯一目标平台 —— 所以这个时机必须显式处理。
