# 勃艮第城堡 · 单机 PWA（手机单人 + AI 对战）可行性评估与开发方案

> 版本 v1.0 ｜ 目标：只给自己玩的单人版，离线可用，手机浏览器可"添加到主屏幕"
> 不评估商业与版权风险（用户明确声明）

---

## 0. 结论先行

**技术可行性：高。可以做到"手机上体验接近原版、AI 对手有中等强度"。**

理由（三条，按重要性排序）：

1. **《勃艮第城堡》几乎没有隐藏信息。** 六个仓库的板块正面全部公开、黑市公开、货物公开、双方领地/银币/工人/仓储全部公开。唯一的随机性是**骰子**和**板块袋的抽取顺序**。这意味着 AI 不需要处理"对手手牌推断"这类难题——用期望最大化（expectimax）或"对牌堆顺序做确定化后 MCTS"就能做出不错的 AI。这是本作能被单人化的最大红利。
2. **规则复杂度集中在"数据 + 效果表"，而不是引擎算法。** 难点是知识板块（黄）约 20+ 张、建筑（米色）8 种的几十条特例效果，以及 9 张玩家领地版图的布局数据。这些是"录入工作"而非"算法难题"，风险可控但要留时间。
3. **纯前端技术栈完全够用。** 单局状态很小（几十 KB 的 plain object），一局 25 轮，手机性能绰绰有余。PWA（vite-plugin-pwa）离线、安装、存档都是成熟方案。

**主要风险（不是技术，是规则保真度）：**

- 原版是 2–4 人游戏，**没有官方单人模式**。单人化必须自己设计（见第 5 节），且设计质量直接决定好不好玩。
- **规则细节必须以官方规则书为准。** 我核对了两个二手资料源（英文 Wikipedia、myboardgameguides.com），已经发现至少两处疑似错误（例如"放船时取哪个仓库的货物"写成了"任意仓库"）。规则录入必须逐条核对规则书并写成测试，否则会出现"能玩但算分错"的隐性 bug。
- 无原版美术资源可用。用自绘 SVG 符号 + 颜色 + 数字三重编码，可读性可以做到不低于原版，但需要 UI 打磨。

## 1. 游戏本体结构分析（可行性论证的依据）

### 1.1 流程规模

| 项目 | 数量 | 对工程的含义 |
|---|---|---|
| 阶段 Phase | 5 | 阶段开始要清场+重新铺 6 个仓库+黑洞+货物 |
| 每阶段轮数 | 5 | 共 25 轮 |
| 每轮每人行动 | 2 颗骰子 → 2 次行动 | 每人每局约 50 次决策 |
| 一局总决策数 | 约 100 次 | MCTS 时间预算的约束条件 |
| 玩家领地六边形格 | 约 37 格/张，共 9 张 | 纯数据录入 |
| 知识板块（黄） | 20+ 张，效果各不相同 | 需要"效果系统"，不能硬编码 |
| 建筑（米色） | 8 种，各有即时效果 | 同上 |
| 货物 | 6 色，终局每块 1 分 | 简单 |
| 奖励板块 | 12 块 | 抢首个填满某色全部区域的奖励 |

### 1.2 动作空间（AI 复杂度的关键）

一次决策的合法动作大致是：

- 用骰子取一块板块（骰子点数 → 对应编号仓库；点数为 1–6，每个仓库有货则最多 1 个选择，但可用工人把点数 ±1 → 相邻 2 个仓库）→ 约 1–3 个"取"动作
- 把仓储里的板块放进领地（同色 + 同数字空格，且需相邻）→ 每块仓储板块约 0–3 个落点
- 卖掉某色货物（骰子点数 = 颜色）→ 最多 6 个选择
- 取 2 个工人 → 1 个选择
- 摆船（放在对应编号的河流格）+ 取货 → 少量选择
- 买黑市板块（2 银币，自由行动，可与其他行动组合）→ 组合爆炸点，但可约束为"可选附加动作"
- 城堡额外行动（可视为再来一次任意点数）

**单次决策合法动作数：约 10–40 个，结构性良好。** 不是围棋那种 300+，也不是那种"每步只有 3 个选择"的退化。

### 1.3 随机性结构（AI 设计的核心）

| 随机源 | 已知/未知 | 处理方式 |
|---|---|---|
| 骰子 | 当轮开始时全部公开 | 期望值计算（概率分布明确） |
| 板块袋抽取顺序 | 未知 | 确定化（determinization）+ 多次采样 |
| 货物袋顺序 | 未知 | 同上（影响很小） |
| 阶段补给结果 | 补给后即公开 | 无 |

**结论：这是一个"近乎完全信息 + 有限随机"的游戏。** 适合的做法是：

- 引擎提供 `clone()` + `setBagOrder(...)` → AI 可以在采样出的确定化世界上跑 rollout；
- 或者更简单：因为单局决策少、动作少，**1–3 ply 的期望最大化 + 强启发式**就能达到"能赢过休闲玩家"的水平。

## 2. 单人模式设计（这是好不好玩的分水岭）

原版 2–4 人，无官方单人模式。三个可行方案：

| 方案 | 做法 | 优点 | 缺点 | 工作量 |
|---|---|---|---|---|
| **A. 分数挑战** | 不设对手，25 轮内最大化自己的分数，配"目标分/星级"体系与随机化开局 | 实现最简单；引擎不用写对手逻辑；复玩靠刷分 | 缺对抗感；抢仓库/抢奖励板块的张力消失（而这是本作核心乐趣） | 0.5 天 |
| **B. Automa 对手**（推荐 v1） | 一个"拟人对手"占真领地、真骰子、真板块，但按简化决策表行动（优先级：补完区域 > 抢可得板块 > 资源 > 卖货） | 保留全部对抗张力（抢板块、抢先手、抢奖励板块、抢区域）；实现快；可解释、可调难度 | 长期会摸清套路 | 1.5–2.5 天 |
| **C. 完整 AI 对手**（推荐 v2） | 真搜索型 AI（期望最大化 / MCTS），以即时期望收益打底 | 复玩性最好；能持续变强 | 评估函数调参耗时；有"太强不好玩"的反向风险 | 3–5 天 |

**建议路线：先做 B 打通全流程 → 再用 C 替换 B 的决策函数（接口不变）。** 因为 B 和 C 都用同一套引擎接口（`getLegalMoves` → 选一个 → `applyMove`），可以先用 B 上线，后续把"选动作"这一步换成 MCTS 即可，是纯粹的替换式升级，不会推翻架构。

**同时保留 A 作为独立模式**（基本免费，因为引擎已支持"不创建对手"的对局），给"我就想安静地刷分"的场景。

**难度分级不靠作弊**（不给 AI 偷看好骰子），而是靠：
- 搜索深度 / 时间预算（0ms / 200ms / 2s）
- 决策噪声（按概率选次优解，模拟人类失误）
- 可选"让先"（AI 起始工人数 -1 等 handicap）

## 3. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript（strict） | 引擎是纯逻辑 + 大量查表，类型能挡掉大量低级错误 |
| 构建 | Vite | 快，PWA 插件生态成熟 |
| UI | React 18 + Vite | 组件化适合"多面板 + 状态驱动"的桌游界面；生态最熟 |
| 棋盘渲染 | **SVG（不用 Canvas/WebGL）** | 单屏最多约 80 个六边形，SVG 性能足够；矢量在任意 DPI 清晰；点击命中检测和 CSS 过渡动画几乎免费 |
| 状态管理 | zustand（或 React reducer + context） | 引擎持有唯一真相，UI 只是视图层；状态小，不需要复杂方案 |
| 样式 | CSS Modules + CSS 变量（含暗色主题） | 无额外依赖，离线友好 |
| PWA | vite-plugin-pwa（Workbox） | 预缓存 + 离线优先，一行配置起步 |
| 存档 | IndexedDB（idb-keyval）+ 导出/导入 JSON | 状态可序列化，快照栈即可实现无限撤销 |
| AI 运行 | Web Worker | 搜索不卡 UI；主线程保持 60fps |
| 测试 | Vitest + 自对弈不变量测试 | 规则保真的唯一可靠手段 |
| 包管理 | pnpm | 环境已有 |
| 部署 | Cloudflare Pages / GitHub Pages（HTTPS） | iOS 安装 PWA 必须 HTTPS；纯静态，零后端 |
| 美术 | 自绘 SVG 符号集（不用原版素材） | 避免素材获取问题；矢量、体积小、可换主题 |

**架构上不引入 monorepo**（对个人项目是纯负担），改用单包 + 目录 + import 边界约束：

```
CastlesOfBurgundy/
├─ docs/
│   └─ 开发方案.md
├─ rules/                       # 规则核对笔记 + 原始规则书 PDF（不进构建）
├─ public/
│   ├─ icons/                   # PWA 图标（192/512/maskable/apple-touch）
│   └─ tiles/                   # 自绘 SVG 板块符号
├─ src/
│   ├─ engine/                  # ★ 纯逻辑：禁止 import react / DOM / window
│   │   ├─ types.ts             # GameState / Tile / PlayerState / Action
│   │   ├─ data/
│   │   │   ├─ boards.ts        # 9 张玩家领地版图布局（六边形坐标 + 颜色 + 数字）
│   │   │   ├─ tiles.ts         # 各色板块清单（含知识板块 20+ 条）
│   │   │   ├─ buildings.ts     # 8 种建筑效果
│   │   │   ├─ knowledge.ts     # 知识板块效果表
│   │   │   └─ scoring.ts       # 区域完成分数表 / 阶段奖励表 / 奖励板块
│   │   ├─ rng.ts               # 可复现种子随机（mulberry32 之类）
│   │   ├─ setup.ts             # 2 人局初始化
│   │   ├─ moves.ts             # getLegalMoves / applyMove / 校验
│   │   ├─ effects.ts           # 效果系统：事件钩子（放置后/阶段末/终局）
│   │   ├─ scoring.ts           # 计分与终局结算
│   │   └─ __tests__/
│   ├─ ai/                      # 依赖 engine，禁止依赖 ui
│   │   ├─ heuristic.ts         # 局面评估
│   │   ├─ automa.ts            # 方案 B：优先级决策表
│   │   ├─ mcts.ts              # 方案 C：确定化 + 期望最大化 / MCTS
│   │   ├─ difficulty.ts        # 时间预算 / 噪声
│   │   └─ worker.ts            # Web Worker 入口
│   ├─ ui/
│   │   ├─ components/          # HexBoard / Depot / Storage / PlayerPanel / Die …
│   │   ├─ screens/             # 主界面 / 设置 / 规则速查 / 结算
│   │   ├─ hooks/
│   │   └─ styles/
│   ├─ store/                   # 对局状态 + 撤销栈 + 自动存档
│   └─ main.tsx
└─ vite.config.ts               # 含 PWA 配置
```

**三条架构红线（决定了这个项目会不会烂掉）：**

1. `engine` 不理解 React，不碰 DOM，不读 `Date.now()`，所有随机来自传入的 seed。→ 可测试、可回放、可给 AI 克隆。
2. `GameState` 必须 100% JSON 可序列化（不存 Map/Set/函数/类实例）。→ 撤销 = 快照栈；存档 = `JSON.stringify`；AI = `structuredClone`。这个决定让后续三件事全部白送。
3. `applyMove(state, action) → { state, events[] }`。events 用于 UI 动画和中文日志。UI 不自己推算规则。

## 4. AI 设计

### 4.1 分级

| 难度 | 算法 | 时间预算 | 预期水平 |
|---|---|---|---|
| 轻松 | 启发式贪心 + 高噪声 | < 20ms | 会犯错，适合熟悉规则 |
| 普通 | 启发式贪心（完整权重表） | < 50ms | 稳定，会抢板块、会补区域 |
| 困难 | 期望最大化 1–2 ply（对骰子求期望、对牌堆确定化采样 N 次） | 0.5–2s | 明显强，会做长线区域规划 |
| 专家（可选） | MCTS + 启发式 rollout 引导，时间预算可配 | 2–5s | 强，但可能"太强" |

### 4.2 评估函数要素（决定 AI 像不像人）

- 区域完成进度：每块未完成区域的"还差几格" → 越接近完成权重越高（配阶段奖励表：前期完成分数更高）
- 颜色连通块与"该色首次完成"的奖励板块争夺
- 即时收益：区域完成分（查表）+ 阶段奖励分
- 资源：工人（骰子调整弹性）、银币（黑市购买力）、货物（终局 1 分/块 + 卖货得分）
- 仓储占用与"下一手能否落位"（引擎可直接算出落点存在性）
- 知识板块协同：如"建筑调整骰子 ±1"配合大量建筑
- 剩余轮数：`25 - 已用轮数`，判断"某区域是否来得及完成"
- 对抗项：对手只差 1 格就能完成的区域、仓库里只剩 1 块的稀缺板块

### 4.3 工程要点

- AI 只允许通过 `getLegalMoves` / `applyMove` / 公开的状态字段访问游戏 → 天然不可能作弊，也便于把 AI 换成人类玩家做自对弈测试。
- **AI vs AI 自对弈 1000 局作为回归测试**：断言不变量（资源非负、板块总数守恒、轮数恰为 25、无非法状态、无死循环），并统计胜率分布，用来验证难度分级是否真的分开了。
- 评估函数权重集中在一个 `WEIGHTS` 常量表里，配合自对弈做粗调（可以写个脚本跑大批对局做参数扫描），不要散落在代码里。

## 5. 开发阶段计划

### 阶段 0：规则数字化（必须先做，且必须逐条核对规则书）
**产出**：`rules/` 下的规则核对笔记（逐条标注"规则书页/条款 → 代码位置 → 对应测试"）+ `engine/data/` 全部数据表（板块、版图、分数表）。
**验收**：数据表能被独立脚本加载并打印出"2 人局初始局面"，且与规则书设置章节逐项对照一致。

### 阶段 1：引擎核心
**产出**：可复现随机的 `GameState`、`getLegalMoves`、`applyMove`、效果系统（事件钩子）、计分（含阶段结算与终局结算）、完整测试套件。
**验收**：命令行能跑完整的 2 人局（两个随机玩家）；50+ 条规则单元测试通过；1000 局自对弈无不变量违例。
**这是全项目最关键的一段**，规则错误拖到 UI 阶段会非常痛苦。

### 阶段 2：可玩 UI（MVP 核心）
**产出**：手机竖屏布局（我方领地为主视图、对手领地可折叠、中央版图用分页/抽屉放六个仓库+黑市+货物+奖励板块）；点选→高亮合法落点→确认的交互模型；中文日志；撤销/重做；提示（用 AI 打分高亮推荐动作）。
**验收**：真机上完整打完一局（先用随机 AI），无遮挡、无误触、核心按钮拇指可达。

### 阶段 3：PWA 化
**产出**：manifest + Workbox 预缓存 + 图标 + iOS meta（`apple-mobile-web-app-capable`、apple-touch-icon、启动图）+ 安装引导 + 版本更新提示 + IndexedDB 自动存档 + 导出/导入 JSON + `overscroll-behavior:none`（防下拉刷新）+ safe-area 适配。
**验收**：飞行模式下从主屏幕图标启动并完整打完一局；删掉本地存档后可从导出的 JSON 恢复。

### 阶段 4：AI 对手（方案 B → C）
**产出**：`automa.ts` 优先级决策表 → 替换为 `heuristic.ts` + `mcts.ts`；Web Worker 化；四档难度；难度分级用自对弈胜率验证。
**验收**：困难档在自对弈中明显压制普通档；单次决策不阻塞 UI。

### 阶段 5：打磨
动画（板块落位、骰子、计分飘字）、音效（可选，需自备免版权音源）、规则速查面板（含知识板块释义）、结算界面与战报、"再来一局"、暗色主题、iPad/横屏适配。

## 7. 必须在阶段 0 逐条核对的规则清单

下面每一条我都会在规则书里找到原文，写成一条测试，再写代码。**列出它们本身就是风险管理的核心**——二手攻略在这些点上普遍不可靠。

**回合结构**
- [ ] 一轮中玩家是"一颗骰子做一次行动、轮流交替"，还是"一次用完两颗骰子"（two sources 说法冲突，必须确认）
- [ ] 白色骰子的确切作用（是否每轮由先手掷、如何决定货物落位、谁持有）
- [ ] 先手标记/顺位轨的精确移动规则与抢占叠放规则
- [ ] 城堡（深绿）"额外行动"的具体范围（是否可自由选点数、能否再触发城堡）

**行动细则**
- [ ] 取板块动作：从"点数对应的编号仓库"取，取到的板块进入**仓储区**（不是直接放置）
- [ ] 仓储区容量（是否为 3 格）、溢出时"必须先弃一块"的精确时序
- [ ] 放置规则：必须同色 + 同数字 + **相邻**（相邻的定义：是否含斜向六边） + 是否可从任意已有板块出发

## 8. 手机端体验专项设计

- **布局（竖屏优先）**：上半屏 = 对手领地缩略图（可点击放大）+ 中央版图横向分页；下半屏 = 我方领地（支持双指缩放/拖动）。固定底部操作条放"确认 / 撤销 / 提示 / 规则"。
- **交互模型**：**点选 + 高亮 + 确认，不做拖拽。** 手机上拖拽小六边形极易误操作，且拖拽在手势冲突（滚动/缩放）下很难做稳。
- **触控规范**：可点目标 ≥ 44×44 CSS px；六边形格子在最小缩放下也要能点准（必要时"放大选格"辅助模式）。
- **防误触**：`overscroll-behavior: none`（禁下拉刷新）、禁用长按选择、`touch-action: manipulation`（去 300ms 延迟）；返回键/侧滑后退要拦截提示。
- **可读性**：板块用 颜色 + 图形符号 + 数字 三重编码，不用纯色区分；内置"知识板块释义"浮层，点任意黄色板块即显示效果原文。
- **刘海与安全区**：`env(safe-area-inset-*)`。
- **性能**：只对变化的 DOM 做 CSS transform 动画；AI 在 Worker 里跑，主线程永不卡。
- **iOS 现实约束**：必须 HTTPS 才能装；无 `beforeinstallprompt`，需要手写"分享 → 添加到主屏幕"引导；iOS 有清理长期未使用站点存储的策略 → 因此**导出/导入 JSON 存档**是必需功能，不是可选项。
